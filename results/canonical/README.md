# Canonical run artifacts

Every file here is the direct, unedited output of `vedaksha-parity
run-config`, committed exactly as produced — never hand-edited, never
regenerated by hand-typing a number into `docs/tiers.md`. Each
`<tier>-<oracle>-<timestamp>.json` carries the full run record (Vedaksha
version + settings, oracle version + settings, case-generation
parameters) followed by every single case's row: the case itself, the
engine's raw answer, the oracle's raw answer, and the full comparison —
nothing aggregated away. The matching `.md` file is a generated,
human-readable digest of the same JSON, never an independent source.

## Reproducing this directory

```
vedaksha-parity run-config configs/all-tiers-200-birthbank-v2.yaml --out results/canonical
vedaksha-parity run-config configs/all-phase-b-tiers.yaml --out results/canonical
```

against the exact `vedaksha` version pinned in `pyproject.toml`
(`pip install --force-reinstall --no-cache-dir vedaksha==X.Y.Z` first —
see `docs/tiers.md`'s reproducing-results note for why that flag matters).
`SHA256SUMS` records this directory's own contents at commit time, so a
later regeneration can be diffed against it byte for byte.

## What this is not

Not every result this project has ever produced — this is the canonical
configs' own output specifically (`configs/all-tiers-200-birthbank-v2.yaml`,
`configs/all-phase-b-tiers.yaml`), the two configs `docs/tiers.md` itself
cites throughout. A one-off investigative run (a letter-response finding,
an ad hoc sweep) stays exactly that — ad hoc, not promoted here — unless
it becomes one of the two canonical configs above.

## Environment this run actually used, stated plainly

This particular commit's artifacts were generated in an environment with
**no Swiss Ephemeris `.se1` data files installed** — every Swiss
Ephemeris comparison here answered via the Moshier analytical fallback,
not true Swiss Ephemeris numerical integration. This is not hidden: the
oracle's own `NAME` field in every affected file states the exact
backend tally (e.g. `Swiss Ephemeris (mixed backends: {'MOSEPH': 3200,
'SWIEPH': 400})`), and `settings()` records it per run. A run with `.se1`
files installed, or with `SwissephOracle(require_swieph=True)`, would
answer differently and more precisely for the Swiss comparisons
specifically — every other oracle here is unaffected by this.
